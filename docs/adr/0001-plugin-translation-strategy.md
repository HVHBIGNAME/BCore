# ADR-0001: Стратегия совместимости Java-плагинов

- Статус: принята
- Дата: 2026-09-02
- Область: `bcore-plugin-java`

## Контекст и требования

BCore — нативный Rust-сервер Minecraft Java Edition с целью vanilla-паритета для протокола 776 (26.2). Нужна собственная нативная плагинная система, но также практическая совместимость с существующими Bukkit/Spigot/Paper-плагинами. Многие плагины обфусцированы, поэтому решение не должно зависеть от восстановления исходных имён и устойчивого анализа байткода.

## Варианты

### Вариант A: JVM-виртуализация

Встроить JVM, загрузить оригинальный `.jar` и предоставить Bukkit/Spigot/Paper API через Java-заглушки. Заглушки регистрируют `native`-методы и передают операции в BCore через JNI. Жизненный цикл плагина (`onEnable`, далее события и команды) остаётся Java-кодом.

### Вариант B: разовая AOT-трансляция

Проанализировать байткод, перевести его в набор нативных вызовов и исполнять без JVM.

## Сравнение

| Критерий | A: JVM | B: AOT |
|---|---|---|
| Производительность | Расход JVM/JNI, JIT может ускорять Java-код | Потенциально ниже runtime overhead после трансляции |
| Сложность | Высокая, но с известной JVM-семантикой | Очень высокая: полный Java bytecode/runtime и транслятор |
| Обфускация | Работает с оригинальным байткодом | Ломает анализ, динамическую загрузку и reflection |
| Безопасность | Нужны sandbox/лимиты и политика классов | Нужны контроль транслятора и нативной памяти |
| API-поверхность | Большая поверхность совместимых заглушек | Нужно моделировать API и runtime в трансляторе |
| Порог входа | Можно добавлять API по мере необходимости | Высокий до первой работающей интеграции |

## Решение

Выбираем Вариант A как костыль для быстрого старта. Он сохраняет совместимость с обфусцированными jar-файлами и позволяет сначала реализовать узкий, востребованный срез API. Это даёт BCore рабочий путь миграции и одновременно подталкивает авторов к переписыванию наиболее критичных плагинов на нативную систему. AOT оставляем для выборочных горячих путей, а не как обязательный pipeline.

## Риски и митигации

- Накладные расходы JVM и GC: отдельная JVM-политика, профилирование, лимиты heap и последующая выборочная JIT/AOT-оптимизация.
- Потокобезопасность JNI: attachment каждого потока, короткие JNI-секции, отсутствие передачи локальных ссылок между потоками.
- Размер Bukkit API: реализовывать контракт по вертикальным срезам; отсутствующие методы выдавать диагностически.
- Маппинг обфусцированных имён: не переводить plugin bytecode; фиксировать стабильный API-заглушек и использовать metadata/descriptor там, где это необходимо.
- Паника через FFI-границу: не пропускать panic через JNI; конвертировать ошибки в Java exceptions и Rust `Result`, добавить boundary tests.
- Безопасность: ограничить classpath/политику загрузчика, явно документировать отсутствие полноценного sandbox в прототипе.

## Вехи

- M1: JVM и jar загружаются, вызывается `onEnable`.
- M2: `getServer()`, `getLogger()`, `registerCommand` работают через заглушки.
- M3: события сервера пробрасываются в Java.
- M4: выборочная JIT/AOT-трансляция горячих путей.

## Альтернативы

- Собственная WASM-плагинная система как основной путь — `bcore-plugin`; она безопаснее и естественнее для нативного ядра, но не заменяет совместимость с Java.
- Pumpkin-подобный API: хорош для нативных плагинов, однако требует отдельного ecosystem/API и не запускает существующие Bukkit jar.
